## Development instruction review

Existing AGENTS.md remains intact apart from a project-specific addendum. Preserve least privilege, user-context preference, valid app-root CLI usage, manifest linting, clear code comments, package-manager installs, and Forge-hosted simplicity.

The addendum records current user overrides and working practices. Legacy UI Kit restrictions apply only to UI Kit surfaces; DOM and ordinary React components are valid in this app's Custom UI iframe. The older storage wording must not be interpreted as an invented `.asApp()` storage API. No platform-specific CLI installation syntax should be copied without checking Bitbucket workspace options.


## Phase 1A update — 2026-10-31

- ADR-009 was open at this point, because npm resolution could not complete in the restricted session. It is now accepted; see the table above.
- ADR-010 (accepted within Phase 1A scope): distinguish environment failures from source failures. EAI_AGAIN is a DNS symptom here; EROFS and EPERM independently demonstrate filesystem/network restrictions. Do not change host DNS, WSL, registry, TLS verification, or permissions without an evidence-backed proposal and approval. See [validation](VALIDATION.md).
- ADR-005 remains open; recommendation refined: prioritize the existing Bitbucket panel. Native multi-app compatibility does not document Bitbucket-to-Jira/Confluence access. Adding scopes, switching to asApp, or assuming user access is insufficient. See [official compatibility documentation](https://developer.atlassian.com/platform/forge/app-compatibility/).
- ADR-011 (proposed, not approved): evaluate either an installed Jira/Confluence companion plus authenticated exchange, or a developer-owned Atlassian 3LO integration. 3LO is documented for user-authorized REST access, but Forge withProvider support for Atlassian OAuth and the callback/token-hosting design remain unconfirmed. Separate OAuth consent is additional setup even without a Forge product installation. No authentication or external backend implementation is authorized. See [architecture options](ARCHITECTURE.md) and [official 3LO documentation](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/).
- Documentation correction: the architecture capability table now avoids the previous cached Preview/product-list description and records the relevant confirmed limitation: Bitbucket is absent from current documented multi-app combinations. This changes no runtime behavior.

## Migration to Claude Code — 2026-10-31

- ADR-012 (accepted): the human lead's project handoff is authoritative where it differs from earlier planning documents. PRD and roadmap were aligned to it: the submission dates, weekly plan, event-driven analysis as MVP, and a human-approved Jira remediation workflow. Competition facts were later checked against the official rules; see the [PRD](PRD.md).
- ADR-013 (accepted): implement PR metadata reads before BR-009, in the current JavaScript setup, to meet the week 1 goal. BR-009 follows early in week 2 and comes before PR changes and diffs. Approved by the human lead 2026-10-31.
- ADR-014 (accepted): read PR metadata in the frontend with Bridge `requestBitbucket`, so Bitbucket enforces the current user's access. Approved with the `read:pullrequest:bitbucket` scope by the human lead 2026-10-31. Backend, app-context analysis will need its own access design. The `getText` resolver is now unused by the UI and stays until the first real resolver replaces it.
- ADR-015 (open): bonus prize target. The Marketplace bonus conflicts with the judging requirement, because apps submitted for listing cannot be shared by installation link. Teamwork Graph is documented only for apps installed into Jira or Confluence, is in Preview, needs allowlisting, and has no Bitbucket scopes. Rovo and MCP module support for this Bitbucket app is unverified.
- ADR-016 (accepted): replace react-scripts with Vite 8, Vitest 5, React 18.3, and strict TypeScript 5.9 in both packages, with ESLint 10 and typescript-eslint strict rules at the root. Approved by the human lead 2026-11-01. TypeScript 5.9 matches the 5.9.2 compiler bundled with Forge CLI 15; 7.x was not evaluated. Bridge stays on 5.2.0 because 7.x adds production audit findings and nothing requires it yet, which revises ADR-009's plan to revisit it with this migration.
- ADR-017 (accepted): add `read:repository:bitbucket`. Approved by the human lead 2026-11-01. The changed file list redirects to an endpoint that needs it, and the spec lists no route without it. BR-012 repository manifests and later diff analysis are also expected to depend on it. It is broader than pull request data, so the privacy policy must state how it is used, and storing or sending repository content needs a new decision.
- ADR-018 (accepted): explicit service relationships live in a repository `blastradius.json`, read from the pull request's destination commit. JSON avoids a parser dependency, and one repository's map is the first scope. Any validation problem rejects the whole map. Results are labelled configured, not proven; a missing or invalid map, and unmapped files, are shown as unknown. Approved by the human lead 2026-11-01.
- ADR-019 (accepted): make repository evidence the MVP baseline. Jira and Confluence references have three levels: found in pull request text, configured in the map, and live. Only live data may be presented as fetched evidence. Run one time-boxed spike of a separate Jira and Confluence companion app before November 14, leaving the existing app ID untouched. Approved by the human lead 2026-11-01. See the BR-010 findings in [architecture](ARCHITECTURE.md).
- ADR-021 (accepted): adopt the Jira and Confluence companion app for live evidence, as an optional add-on to the repository evidence baseline. Visibility rule: it returns only items the repository explicitly references, and only a title, status, and short excerpt; the admin connecting the apps accepts that repository readers can see those; the panel labels them. This is not a per-viewer permission check, and documentation must say so. Judge setup still needs proving in BR-021, and instructions keep the Jira part optional. Approved by the human lead 2026-11-01. Spike results are in [architecture](ARCHITECTURE.md).
- ADR-022 (accepted): companion connection design. The companion app lives in `companion/` as its own Forge app; a backend resolver calls it so the token never reaches the browser; an admin enters the connection once in a setup screen, stored with `storage:app`; and the backend derives which items to request from the destination map and pull request. Adds `storage:app` and backend egress to `*.webtrigger.atlassian.app`. Approved by the human lead 2026-11-01. Open: the admin permission check, reading the map as the current user from the backend, and the judge flow.
- ADR-020 (accepted): consumers declare used schema fields in `blastradius.json`, compared across the pull request's commits. Approved with ADR-019.
- ADR-005 gains a further input: a Jira or Confluence companion app could also reach Teamwork Graph, subject to allowlisting and organization admin installation. Include this in BR-010.
- ADR-005 remains open with a new input: the compatibility page updated 2026-10-30 says, under Global Apps (EAP), "Confluence, Jira and Bitbucket connections will be supported in EAP." This is future-tense EAP wording, not a supported capability. Include it in BR-010.
